Step 3 extends the existing browser library cache to complete interaction snapshots. This is a development application change; it requires no SQL and does not change the deployed production application or the shared database schema.

The account-scoped V2 envelope contains independently complete ratings, bookmarks, and dismissal collections. Presence means completeness, so `[]` is a confirmed empty collection and a missing property is unavailable. Ratings and bookmarks retain their UUID/ULID mappings. Ratings also carry the available compact card details; missing details do not make the interaction IDs incomplete. No second interaction store or save queue was introduced.

Restoration runs through the existing stores and `libraryLoads.markSnapshot` before the ordinary ID loaders start. The loaders reset refresh status without clearing snapshot availability. Existing rating/bookmark/dismissal readiness checks therefore work during background loading or a failed refresh when their required cached collections are available. Recommendation submission retains its save-flush checks. Cache content supplies UI state, never authentication or server write permission.

The stores apply the existing `librarySaves` revision overlays on both cache restoration and network hydration. Pending additions/removals always win; recently acknowledged changes win over reads started before acknowledgment. Cache restoration uses revision `-1`, since browser persistence predates the current in-memory journal. Snapshots may include optimistic UI values; the independent pending-save journal still determines what needs saving and retains its existing retry/failure notices. Clearing snapshots does not acknowledge or discard pending writes.

V1 ratings-only caches remain readable for display. They were assembled from the available details and may contain fewer rows than the full rated-ID collection, so they do not establish complete ratings or missing bookmark/dismissal readiness. A subsequent successful load writes V2. Legacy display availability does not bypass action gates.

Persistence is bounded to 50,000 entries per collection and a 4,000,000-character serialized envelope, with whole-collection validation, unique identifiers, valid ratings, and owner/version checks. Invalid collections are rejected independently. Writes merge only complete collections, including confirmed empty ones. Uninitialized or failed first-load empty stores cannot replace a good collection. Writes run within a bounded 200 ms delay and flush on `pagehide`; unchanged serialized values do not generate repeated storage events. Blocked storage, quota errors, corrupt data, or oversize snapshots fall back to normal loading. Interaction snapshots currently have no expiry timer; they are revalidated on account activation and relevant cross-tab changes, and cleared for that account on logout/import invalidation. The 24-hour feed-cache policy belongs to Step 4.

ID and rated-detail reads now request exact totals and fetch ranges of up to 500 rows. They continue if the API returns a smaller configured page cap, commit only after the expected number of unique rows is available, and reject missing/changing totals or partial failures. This avoids silently caching a capped response as complete. Most collections still use one HTTP request; large collections require multiple pages. Exact counts add database work. These paged reads are not one database transaction: concurrent remote edits can still require another refresh; local edits retain journal protection. Existing ownership, cancellation, timeout, retry, and error behavior remains in the load controller.

Cross-tab cache events for the current account (including browser storage clearing) revalidate through the existing loaders and invalidate the prepared feed. They do not directly replace the active card list or adopt another tab's UI values. Other accounts' cache events are ignored. Bursts share an in-flight revalidation with at most one queued follow-up per read. Persistence pauses during this reconciliation so an older local snapshot cannot immediately overwrite another tab's update; after failure it remains paused until all ID collections refresh successfully. Account changes cancel pending cache timers; owner checks prevent late work from persisting under another account. Logout/import invalidation clears only the affected account's disposable V1/V2 snapshots, retaining other accounts' caches and all pending-save journals. This does not add shared ownership or locking to the existing save queue across tabs.
