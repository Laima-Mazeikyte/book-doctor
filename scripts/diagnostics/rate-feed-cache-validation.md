Step 4 adds persistent feed candidates to the development application. No SQL or production deployment is required. Production keeps its existing application against the shared database.

The layout's existing feed controller uses an optional browser cache under `book-doctor:rate-feed:v1:<user-id>`. Each snapshot contains its owner, format version, fetch timestamp, source, and up to 100 unique books. It keeps the most recent two displayed batches when pagination grows the list. Card fields include full summary, year, genres, catalog type, quality band, and cover URL, so expanding a restored card still works. It stores no access tokens, counts, pending-save state, or generation status. A request ID is a source hint only.

Snapshots expire 24 hours after their last confirmed read. Restoring, navigating, and reading storage do not extend that timestamp. The existing five-minute in-memory prepared-result policy remains. Fresh personalized results take precedence over older disk candidates, without reading browser storage on the common warm path. A popular snapshot can reuse recent below-threshold validation during repeated navigation without duplicate feed/popular reads. Parsing checks owner/version, timestamps, unique UUIDs/ULIDs, source fields, card fields, and size. Limits are 100 books and 1,500,000 serialized characters. Invalid, expired, oversized, or unavailable storage falls back to ordinary loading. Writes have a bounded 200 ms delay, flush on navigation departure, `pagehide`, and controller destruction, and tolerate quota/blocked-storage failures.

The page waits for session restoration and the layout's interaction restoration before admitting a disk snapshot. All three interaction collections must have complete snapshots; a partial or legacy-only library follows fresh loading. Candidates are filtered against ratings, bookmarks, dismissals, and the existing pending/recently acknowledged save overlays before mounting. A completely excluded snapshot follows the ordinary fresh path. If a recent in-memory candidate list has become completely excluded, it is revalidated before falling back. Initial cold data filtered to empty uses the existing public fallback instead of rendering an empty grid.

Personalized candidates are admitted only when the current local interaction snapshot meets the feed threshold. Popular snapshots retain their seed, next offset, and `hasMore`; they are persisted/restored only with complete zero-interaction state. A public fallback after a personalized-feed failure is not saved as a new popular snapshot, so it cannot suppress the next entry's ordinary personalized generation decision.

A restored grid starts a read-only refresh of the same controller resource. It never calls the initial generation callback. Refresh results update prepared/disk candidates without replacing the active list, book objects, order, or scroll position. An authoritative empty/ineligible result retires old personalized disk candidates for the next admission; a failed refresh retains them. HTTP 401/403 invalidates reusable memory and disk data, while mounted content still follows the existing auth-store lifecycle. Local actions invalidate prepared responses, but retain filterable disk candidates; otherwise every rating would make the next reload cold. A read started before that invalidation cannot save an obsolete response.

Pagination progress/dwell is initialized from the current mount. No timers, scroll credit, or in-flight job state are restored. Pagination reads live feed metadata, appends newly available unique candidates first, and creates a generation job only if none are available and current status permits it. A failed status read now stops that attempt with the existing error/retry behavior. It cannot fall through into generation using a persisted pointer. Generation polling/completion continues through the existing guarded page operations and save-flush checks.

Logout explicitly clears that account's persisted feed and queued cache writes. Account switches clear the visible list and reject old responses. Layout destruction flushes storage rather than treating a reload as logout. Snapshot cleanup never touches interaction caches or pending-save journals. Cross-tab feed writes are candidates for later admission and do not replace mounted cards; existing interaction-cache events still invalidate prepared data and revalidate the relevant account.

`createBrowserRateFeedController({ persistSnapshots: false })` disables feed persistence/admission without changing the save queue. The pure controller also accepts no cache or an injected cache for controlled tests. Construction performs no browser-storage reads or network requests, and controller state remains scoped to the layout. Personalized `/api/feed/latest` responses explicitly send `Cache-Control: private, no-store`; this browser-owned snapshot does not introduce a shared HTTP/CDN cache.
